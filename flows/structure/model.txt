=== FLUJO: Internacionalizacion (feature-i18n-localization) ===

No tiene entidades propias. Agrega la columna `locale` (string, es/en) a:
- Order (feature-direct-purchase)
- Quote (feature-custom-quote)
- Complaint (feature-complaints-refunds)

El locale se persiste con el registro al momento del submit (header X-Locale)
y se usa para seleccionar el template de email cuando el sistema envia
comunicaciones para ese registro.

=== RELACIONES CROSS-FLOJO ===

1. Order.payment_service_ref -> Payment.reference_id
   Relacion cross-microservicio: api-core (PostgreSQL/Supabase) -> payment-service (propia DB).
   order_id de api-core se usa como reference_id en payment-service.

2. Quote.payment_service_ref -> Payment.reference_id
   Misma relacion que Order pero para el Flujo B. quote_id de api-core
   se usa como reference_id en payment-service.

3. Complaint.reference_id -> Order.id | Quote.id
   Un reclamo puede apuntar a una orden (Flow A) o una cotizacion (Flow B).
   Si el cliente no tiene la referencia, reference_type=unknown y reference_id=null.

4. Complaint.refund_request_id -> Refund.refund_request_id
   Relacion cross-microservicio para idempotencia. api-core genera un
   refund_request_id unico por intento de negocio, payment-service lo
   usa para evitar reembolsos duplicados.

5. DeliveryItem = UNION de Order (status=accepted) + Quote (status=paid)
   Proyeccion de solo lectura que unifica ambos flujos en una sola vista
   de entregas pendientes. No es una tabla, es un SQL view o calculo en
   el use case.

6. AdminNotification es polimorfica via reference_type + reference_id
   Puede apuntar a Order, Quote, Complaint o Supply segun el tipo
   de notificacion.

7. Prototype.stock_qty vs Supply.current_qty
   Conceptos separados: Prototype.stock_qty es producto terminado
   (se descuenta al aceptar orden). Supply.current_qty es materia prima
   (se consume en fabricacion). No estan directamente relacionados en el
   modelo de datos actual.

8. Receipt.payment_id / Receipt.refund_id -> Payment.id / Refund.id
   Receipts pueden provenir de un pago o de un reembolso. Ambos FK son
   nullable. Un receipt siempre es de un tipo o del otro, nunca ambos.

=== RESUMEN DE BASES DE DATOS ===

Base de datos 1: PostgreSQL (Supabase) - api-core
  Tablas: AdminUser, RefreshToken, Prototype, ProtoImage, Order, Quote,
          Complaint, Supply, SupplyStockChangeLog, LowStockAlertState,
          AdminNotification
  Views/Proyecciones: DeliveryItem (UNION Order accepted + Quote paid)

Base de datos 2: payment-service (propia, separada)
  Tablas: Payment, Refund, Receipt, AuditLog
  Comunicacion con api-core: HTTP + Webhooks, nunca comparte DB.
